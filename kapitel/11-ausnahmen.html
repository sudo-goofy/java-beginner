11.1 Ausnahmen und Stacktrace

Bevor du einen Absturz auffängst, musst du ihn lesen können. Die Meldung sagt dir, was passiert ist, wo, und wie weit das Programm noch kam.

AUFBAU · KLICK AUF EINEN TEIL

Exception in thread "main" Paket.Sorte der Ausnahme: Grund im Klartext
   at Klasse.Methode(Datei:Zeile)

Darüber steht auf der Konsole, was das Programm vor dem Absturz noch ausgegeben hat.

Exception in thread "main" leitet die Meldung ein: Im Hauptablauf des Programms wurde eine Ausnahme geworfen und von keinem catch gefangen. Deshalb hat die JVM das Programm beendet.
Paket: wo die Klasse der Ausnahme liegt, etwa java.lang oder java.util. Bei java.lang brauchst du für ein catch keinen Import, bei java.util schon.
Sorte der Ausnahme: der Name ihrer Klasse, etwa ArrayIndexOutOfBoundsException. Der Name beschreibt das Problem: ein Index außerhalb der Grenzen des Arrays. Genau diesen Namen schreibst du später in die Klammer hinter catch.
Grund im Klartext: die Nachricht der Ausnahme, etwa Index 5 out of bounds for length 3. Sie nennt oft die Werte, die nicht gepasst haben. Im Programm liefert sie e.getMessage().
Klasse und Methode: wo die Ausnahme geworfen wurde, etwa at Crash.main: in der Methode main der Klasse Crash. Stehen mehrere at-Zeilen untereinander, such die oberste, die eine deiner eigenen Klassen nennt.
Datei und Zeile: die Quelldatei und die Zeilennummer darin, etwa Crash.java:7. Dort steht die Anweisung, die die Ausnahme ausgelöst hat, hier temperatures[5].

Drei Elemente im Array, ein Zugriff auf Index 5. Führ aus und achte darauf, was auf der Konsole landet, und vor allem, was nicht.

public class Crash {

    public static void main(String[] args) {
        int[] temperatures = {18, 23, 19};

        System.out.println("All good so far.");
        System.out.println(temperatures[5]);
        System.out.println("This line is never reached.");
    }

}

Merk dir das

Eine Ausnahme („Exception“) ist kein Syntaxfehler. Das Programm läuft, und mitten im Lauf lässt sich eine Zeile nicht ausführen. Java wirft eine Ausnahme und beendet das Programm. Das ist nur das Standardverhalten, und das kannst du ändern.

Das Panik-Wörterbuch zeigt, wie du die zehn häufigsten Fehler wegmachst. Hier geht es um die, die sich nicht wegmachen lassen: Schuld ist nicht dein Code, sondern die Eingabe.

11.2 Ausnahmebehandlung mit try und catch

try heißt „versuch es“, catch „fang es auf“. Zusammen wirken sie wie ein Sprungnetz: Der Code, der eine Ausnahme werfen kann, kommt in den try-Block. Wird dort eine Ausnahme geworfen, landet sie im catch-Block.

AUFBAU · KLICK AUF EINEN TEIL

try {
    Code, der schiefgehen kann
} catch (Sorte der Ausnahme e) {
    was dann passieren soll
}

Nach dem catch läuft das Programm normal weiter, mit der ersten Zeile hinter seiner schließenden Klammer.

try leitet den try-Block ein. Wird darin eine Ausnahme geworfen, bricht Java den Block an dieser Stelle ab und sucht einen passenden catch-Block. Die restlichen Zeilen im try-Block werden übersprungen, nicht nachgeholt.
Code, der schiefgehen kann: die Anweisung, die eine Ausnahme werfen kann, etwa System.out.println(temperatures[5]);, und was direkt von ihr abhängt. Mehr gehört nicht hinein, denn bei einer Ausnahme fällt alles danach aus.
catch steht direkt hinter der schließenden Klammer des try-Blocks. Sein Block läuft nur, wenn im try-Block eine Ausnahme der genannten Sorte geworfen wurde. Läuft alles glatt, wird er übersprungen.
Sorte der Ausnahme: der Klassenname der Ausnahme, etwa ArrayIndexOutOfBoundsException. Der catch-Block fängt nur diese Sorte: Wird eine andere geworfen, bricht das Programm trotzdem ab.
e ist eine Variable, die das Ausnahme-Objekt aufnimmt. Ihr Name ist frei wählbar, e ist üblich. Was du damit anfangen kannst, zeigt 11.3.
Was dann passieren soll: die Anweisungen im catch-Block, etwa System.out.println("That slot does not exist.");. Lass den Block nicht leer: Sonst läuft das Programm weiter, und niemand erfährt von der Ausnahme.

SafetyNet.java

public class SafetyNet {

    public static void main(String[] args) {
        int[] temperatures = {18, 23, 19};

        try {
            System.out.println("All good so far.");
            System.out.println(temperatures[5]);
            System.out.println("This line is never reached.");
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("That slot does not exist.");
        }

        System.out.println("And on we go.");
    }

}

try {beginnt den try-Block. Abgesichert ist alles bis zur schließenden Klammer.
temperatures[5]wirft die Ausnahme. Java bricht den try-Block an dieser Stelle ab und sucht einen passenden catch.
catch (ArrayIndexOutOfBoundsException e)Die Sorte passt, also läuft dieser Block: „That slot does not exist.“
System.out.println("And on we go.");steht hinter dem catch-Block. Die Ausnahme ist gefangen, das Programm läuft normal weiter.

Dasselbe Programm wie Crash, nur mit try und catch drumherum. Darum geht es im ganzen Kapitel:

ohne try/catchmit try/catch

Die Meldung geht an die Konsole.Du bestimmst, was dort steht.

Und This line is never reached. fehlt: Der try-Block läuft bis zur Ausnahme, der Rest wird übersprungen, nicht nachgeholt. Deshalb gehört in einen try-Block so wenig wie möglich: Je mehr darin steht, desto mehr wird übersprungen.

Merk dir das

catch fängt nur die Sorte in seiner Klammer. catch (ArithmeticException e) fängt keinen Index-Fehler: Das Programm stürzt dann trotz try ab.

11.3 Das Ausnahmeobjekt

Das e in catch (… e) ist eine normale Variable mit dem Ausnahme-Objekt. Objekte haben Methoden (Kapitel 9), die wichtigste hier ist getMessage().

AUFBAU · KLICK AUF EINEN TEIL

catch (Sorte der Ausnahme e) {
    System.out.println(Text + e.getMessage());
}

e hat als Typ die Sorte aus der Klammer. getMessage() liefert den Grund als String.

Sorte der Ausnahme: etwa ArithmeticException. Sie steht vor e wie der Typ vor einem Parameter: erst der Typ, dann der Name.
e enthält die Referenz auf das Ausnahme-Objekt und gilt nur innerhalb des catch-Blocks. Über den Punkt rufst du Methoden dieses Objekts auf, wie bei jedem anderen Objekt.
Text: ein eigener Hinweis vor der Nachricht, etwa "Message: ". Denk an das Leerzeichen vor dem schließenden Anführungszeichen, sonst steht die Nachricht direkt am Doppelpunkt.
Das + verkettet die beiden Strings: Aus "Message: " und "/ by zero" wird Message: / by zero.
getMessage() ist eine Methode des Ausnahme-Objekts. Sie liefert dieselbe Nachricht, die ohne catch in der Absturzmeldung hinter dem Doppelpunkt stünde, etwa / by zero. Die leeren Klammern gehören dazu.

Ausschnitt

try {
    int result = 10 / 0;
    System.out.println(result);
} catch (ArithmeticException e) {
    System.out.println("Message: " + e.getMessage());
}
KONSOLE

ZEILE FÜR ZEILE

int result = 10 / 0;teilt eine ganze Zahl durch 0. Java wirft eine ArithmeticException, das println darunter fällt aus.
catch (ArithmeticException e)fängt sie und legt das Ausnahme-Objekt in die Variable e.
e.getMessage()ruft eine Methode dieses Objekts auf. Sie liefert den Grund als Text: „/ by zero“.

Merk dir das

e.getMessage() liefert den Grund, den die JVM sonst hinter den Doppelpunkt geschrieben hätte, nur jetzt da, wo du ihn haben willst.

11.4 Mehrere catch-Blöcke

Ein try darf mehrere catch-Blöcke haben. Java nimmt von oben nach unten den ersten, dessen Sorte passt: wie ein else if für Ausnahmen.

AUFBAU · KLICK AUF EINEN TEIL

try {
    Code, der schiefgehen kann
} catch (erste Sorte e) {
    Antwort auf die erste Sorte
} catch (zweite Sorte e) {
    Antwort auf die zweite Sorte
}

Die Reihenfolge zählt: Java prüft die catch-Blöcke von oben nach unten.

try: ein einziger try-Block, dahinter beliebig viele catch-Blöcke. Wird darin eine Ausnahme geworfen, bricht der Block an dieser Stelle ab, wie bei nur einem catch.
Code, der schiefgehen kann: Er kann verschiedene Sorten von Ausnahmen werfen. names[2].toUpperCase() etwa wirft bei einem Index außerhalb des Arrays eine ArrayIndexOutOfBoundsException und, wenn das Element null ist, eine NullPointerException. Geworfen wird aber höchstens eine, denn der Block bricht bei der ersten ab.
catch: Jeder Block nennt seine eigene Sorte und hat seine eigene Antwort. Hat einer gepasst, werden alle übrigen übersprungen, auch wenn ihre Sorte ebenfalls passen würde.
Erste Sorte: wird zuerst geprüft, etwa ArrayIndexOutOfBoundsException. Steht hier Exception, fängt dieser Block jede Ausnahme, und die Blöcke darunter kämen nie dran. Dann meldet der Compiler einen Fehler.
Zweite Sorte: wird nur geprüft, wenn die erste nicht gepasst hat, etwa NullPointerException. Passt keine der Sorten, bricht das Programm ab wie ganz ohne try.
Antwort: Jede Sorte bekommt ihre eigene Reaktion, etwa „Index is off.“ für den Index-Fehler und „There was nothing.“ für null. Genau dafür lohnen sich mehrere catch-Blöcke.

Ausschnitt

String[] names = {"Mia", "Paul"};

try {
    System.out.println(names[2].toUpperCase());
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Index is off.");
} catch (NullPointerException e) {
    System.out.println("There was nothing.");
}
KONSOLE

ZEILE FÜR ZEILE

names[2].toUpperCase()names hat nur die Indizes 0 und 1. Schon der Zugriff auf Index 2 wirft die Ausnahme, toUpperCase() wird gar nicht mehr aufgerufen.
catch (ArrayIndexOutOfBoundsException e)der erste catch. Die Sorte passt, also erscheint „Index is off.“
catch (NullPointerException e)wird übersprungen: Es läuft nur der erste catch, der passt.

Merk dir das

Von mehreren catch-Blöcken läuft höchstens einer: der erste von oben, dessen Sorte passt.

catch (Exception e) fängt alles. Bequem, aber selten richtig: Wer alles gleich behandelt, kann nicht unterschiedlich reagieren. Eine falsche Eingabe wiederholt man, einen Index-Fehler repariert man.

11.5 Der finally-Block

Hinter die catch-Blöcke darf ein finally. Es läuft immer: nach glattem Durchlauf genauso wie nach einer gefangenen Ausnahme.

AUFBAU · KLICK AUF EINEN TEIL

try {
    Code, der schiefgehen kann
} catch (Sorte der Ausnahme e) {
    Antwort auf die Ausnahme
} finally {
    Aufräumen
}

Wofür? Zum Aufräumen: Datei schließen, Verbindung trennen, Scanner zumachen. Das muss auch passieren, wenn es schiefging, gerade dann.

try: läuft bis zur Anweisung, die eine Ausnahme wirft. Danach geht es im passenden catch-Block weiter und anschließend im finally-Block.
Code, der schiefgehen kann: etwa System.out.println("Per person: " + sum / people);, das bei people gleich 0 eine ArithmeticException wirft. Zeilen dahinter im try-Block fallen aus.
catch mit Sorte: Der Block läuft nur, wenn im try-Block eine Ausnahme dieser Sorte geworfen wurde. Läuft alles glatt, wird er übersprungen, der finally-Block aber nicht.
Antwort auf die Ausnahme: die Reaktion darauf, etwa System.out.println("Cannot divide by 0 people.");. Erst danach läuft der finally-Block.
finally steht hinter dem letzten catch-Block. Sein Block läuft in jedem Fall: nach glattem Durchlauf, nach einer gefangenen Ausnahme und auch dann, wenn keine Sorte passt und das Programm danach abbricht.
Aufräumen: Anweisungen, die immer nötig sind, etwa keyboard.close(); für den Scanner. Was nur bei Erfolg laufen soll, gehört nicht hierher, sondern in den try-Block.

ZEILE FÜR ZEILE

try { … }läuft bis zur Zeile mit der Ausnahme, der Rest fällt aus.
catch (…) { … }läuft nur, wenn eine passende Ausnahme geworfen wurde.
finally { … }läuft so oder so.

Merk dir das

finally läuft in jedem Fall. Dort wird aufgeräumt.

Aufgabe 11.5.1

Aufgabe 11.5.1: Schreibtischtest mit finally

Lesen statt tippen~10 min

Sag die exakte Ausgabe voraus, bevor du ausführst. Vorsicht bei Done.: Schau dir an, wo die Ausnahme geworfen wird. Danach: Wäre Register closing. auch ohne finally erschienen?

Receipt.java

public class Receipt {

    public static void main(String[] args) {
        int sum = 12;
        int people = 0;

        try {
            System.out.println("The bill is being split.");
            System.out.println("Per person: " + sum / people);
            System.out.println("Done.");
        } catch (ArithmeticException e) {
            System.out.println("Cannot divide by 0 people.");
        } finally {
            System.out.println("Register closing.");
        }

        System.out.println("Goodbye.");
    }

}
KONSOLE
Warum das so ist
  • Done. fehlt, darum geht es: Die Ausnahme wird eine Zeile darüber geworfen, der Rest des try-Blocks wird übersprungen.
  • Register closing. kommt trotzdem, dafür ist finally da.
  • Goodbye. steht hinter dem finally-Block: Das Programm läuft normal zu Ende.

Und ohne finally? Hier wäre Register closing. auch als Zeile hinter dem catch erschienen, denn die Ausnahme ist gefangen. Einen Unterschied macht finally, wenn der catch nicht passt: Dann bricht das Programm ab, alles hinter dem finally-Block fällt aus, aber der finally-Block läuft noch. Deshalb gehört das Aufräumen dorthin.

11.6 Fehlerhafte Benutzereingaben abfangen

Ein Index-Fehler ist dein Fehler: Den reparierst du. Eine falsche Tastatureingabe ist niemandes Fehler: Menschen vertippen sich. Stürzt ein Programm deswegen ab, ist es schlecht gebaut, und genau hier zahlt sich try/catch aus.

AUFBAU · KLICK AUF EINEN TEIL

try {
    Zahl lesen und damit weiterarbeiten
} catch (InputMismatchException oder NumberFormatException e) {
    freundlich um eine neue Eingabe bitten
}

Welche Sorte geworfen wird, hängt davon ab, wie du liest. Das klären die beiden Wege unten.

try: Wirft das Lesen eine Ausnahme, wird der Rest des Blocks übersprungen. So rechnet das Programm nie mit einer Zahl weiter, die gar nicht gelesen wurde.
Zahl lesen und damit weiterarbeiten: etwa int age = Integer.parseInt(raw); und danach die Ausgabe mit age + 1. Beides gehört in den try-Block, denn eine dort deklarierte Variable wie age gibt es außerhalb nicht.
catch fängt nur Ausnahmen aus seinem eigenen try-Block. Steht das Lesen außerhalb, etwa davor, sichert er es nicht ab.
Sorte: nextInt() wirft eine InputMismatchException (Import aus java.util nötig), Integer.parseInt eine NumberFormatException (kein Import nötig). Mit der falschen Type im catch bricht das Programm trotzdem ab.
Freundlich um eine neue Eingabe bitten: eine Meldung, die sagt, was erwartet wird, etwa System.out.println("That was not a whole number.");. Danach läuft das Programm hinter dem catch-Block normal weiter.

Bekommt nextInt() keine ganze Zahl, wirft der Scanner eine InputMismatchException. Sie liegt im selben Paket, braucht aber eine eigene Zeile, denn ein import holt genau eine Klasse (import java.util.*; holt das ganze Paket, verrät aber nicht, was du wirklich brauchst):

ganz oben in der Datei

import java.util.InputMismatchException;
import java.util.Scanner;

Liest du wie in Kapitel 5 mit nextLine() und parst selbst, wirft Integer.parseInt bei twelve eine NumberFormatException. Sie liegt in java.lang wie String, braucht also keinen Import:

Input.java

import java.util.Scanner;

public class Input {

    public static void main(String[] args) {
        Scanner keyboard = new Scanner(System.in);

        System.out.println("How old are you?");
        String raw = keyboard.nextLine().trim();

        try {
            int age = Integer.parseInt(raw);
            System.out.println("Next year: " + (age + 1));
        } catch (NumberFormatException e) {
            System.out.println("That was not a whole number.");
        }
    }

}
KONSOLE

ZEILE FÜR ZEILE

keyboard.nextLine().trim()liest die Eingabe als Text und entfernt Leerzeichen am Anfang und Ende, wie in Kapitel 5.
Integer.parseInt(raw)macht aus dem Text eine ganze Zahl. Bei „twelve“ geht das nicht: Java wirft eine NumberFormatException, die Zeile darunter fällt aus.
catch (NumberFormatException e)fängt genau diese Sorte und gibt einen Hinweis aus, statt das Programm abstürzen zu lassen.

Merk dir das

Der catch muss zur Sorte passen, und die hängt davon ab, wie du liest:

  • nextInt() wirft eine InputMismatchException.
  • Integer.parseInt wirft eine NumberFormatException.

Aufgabe 11.6.1: Der Rechner, der nicht mehr abstürzt

Grundlagen~15 minIDE

Schreib ein Programm, das zwei ganze Zahlen von der Tastatur liest und sie teilt. Zwei Dinge können schiefgehen: Als zweite Zahl kommt eine 0, oder statt einer Zahl kommen Buchstaben. In beiden Fällen soll das Programm nicht abstürzen, sondern selbst eine Meldung ausgeben: Nobody divides by zero. bzw. Please enter whole numbers.

Die beiden Fälle brauchen verschiedene Werkzeuge. Überleg vorher: Welcher gehört in einen catch, welcher nicht?

Zum Ausprobieren eingeben: 12, dann 0. Danach noch einmal mit twelve.

Erwartete Ausgabe:

Konsole

Numerator?
Denominator?
Nobody divides by zero.
Lösung (erst selbst probieren)

Calculator.java

import java.util.InputMismatchException;
import java.util.Scanner;

public class Calculator {

    public static void main(String[] args) {
        Scanner keyboard = new Scanner(System.in);

        try {
            System.out.println("Numerator?");
            int numerator = keyboard.nextInt();
            System.out.println("Denominator?");
            int denominator = keyboard.nextInt();

            if (denominator == 0) {
                System.out.println("Nobody divides by zero.");
            } else {
                System.out.println("Result: " + numerator / denominator);
            }
        } catch (InputMismatchException e) {
            System.out.println("Please enter whole numbers.");
        }
    }

}
KONSOLE

Zwei Probleme, zwei Werkzeuge:

  • Die 0 siehst du kommen: Ein if prüft sie, bevor geteilt wird. Was du selbst verhindern kannst, fängst du nicht, du verhinderst es.
  • Buchstaben statt einer Zahl merkt erst nextInt() beim Lesen: Dafür sind try und catch da.

Das if steht mit im try, weil numerator und denominator nur dort gelten (Kapitel 4).

Legendär 11.6.2: Die Ausnahme, die du selbst wirfstoptional

Neu~20 minIDE

Bisher hast du gefangen, was Java geworfen hat. Werfen darfst du auch selbst, mit throw:

Ausschnitt

throw new IllegalArgumentException("negative quantity: " + quantity);

Die Zeile beendet die Methode sofort wie ein return, gibt aber keinen Wert zurück, sondern die Ausnahme an den Aufrufer weiter. Der fängt sie mit catch, sonst stürzt das Programm ab. So lehnt eine Methode einen ungültigen Wert ab, ohne einen Ersatzwert zu erfinden, den niemand von einem Fehler unterscheiden kann.

Bau eine Methode validate(int quantity), die die Menge zurückgibt, aber bei einer negativen Zahl wirft statt zurückgibt. Die main ruft sie für 5 und -3 auf; der zweite Aufruf landet im catch, das e.getMessage() ausgibt.

Erwartete Ausgabe:

Konsole

Ammo: 5
Rejected: negative quantity: -3
Lösung (erst selbst probieren)

Guard.java

public class Guard {

    public static void main(String[] args) {
        int[] attempts = {5, -3};

        for (int v : attempts) {
            try {
                System.out.println("Ammo: " + validate(v));
            } catch (IllegalArgumentException e) {
                System.out.println("Rejected: " + e.getMessage());
            }
        }
    }

    static int validate(int quantity) {
        if (quantity < 0) {
            throw new IllegalArgumentException(
                    "negative quantity: " + quantity);
        }
        return quantity;
    }

}
KONSOLE

Zwei Dinge sind neu:

  • Hinter throw steht kein return: Die Methode ist danach zu Ende, und der Compiler weiß das.
  • Das try steht in der Schleife, nicht darum herum. Stünde es außen, wäre nach dem ersten abgelehnten Versuch Schluss.

Der Text in der Klammer ist genau das, was getMessage() später liefert. Also gehört dort hinein, was der Aufrufer wissen muss, nicht „Fehler!“.

            System.out.println("Total price: " + quantity * 2.5 + " euros");
        } catch (InputMismatchException e) {
            System.out.println("Please enter a whole number.");
        }

        System.out.println("Next item.");
    }

}
KONSOLE

Die Ausgabezeile muss mit in den try-Block: quantity wird im try deklariert und gilt nur dort (Kapitel 4). Oben braucht es außerdem import java.util.InputMismatchException;.

c) Zwei mögliche Nachteile von catch (Exception e):

  • Es fängt auch, was nicht gemeint war: Index-Fehler, NullPointerException, jeden Programmierfehler. Das Programm läuft scheinbar weiter, und der Fehler fällt erst viel später auf.
  • Wer alles gleich behandelt, kann nicht mehr unterschiedlich reagieren.

Checkpoint

Im try-Block stehen drei println. Beim zweiten wird eine Ausnahme geworfen. Wie viele Zeilen aus dem try-Block erscheinen?

Deshalb gehört in einen try-Block so wenig wie möglich.

Wann läuft ein finally-Block?

Deshalb räumt man dort auf: Datei schließen, Scanner zumachen.

catch (ArithmeticException e) steht um einen Array-Zugriff. Was passiert beim Index-Fehler?

Trotz try stürzt das Programm ab. Die Sorte muss passen.

Welchen Fehler fängst du mit catch, welchen reparierst du?

Was von draußen kommt (Tastatur, Datei, Netzwerk), fängt man auf. Den eigenen Fehler repariert man.

Das Wichtigste in Kürze

  • Eine Ausnahme ist kein Syntaxfehler, sondern ein Ereignis zur Laufzeit.
  • try umschließt den gefährdeten Code, catch (Type e) fängt genau diese Sorte.
  • Im try fällt alles nach der Zeile mit der Ausnahme aus: so wenig wie möglich hineinpacken.
  • finally läuft in jedem Fall. Dort wird aufgeräumt.
  • e.getMessage() liefert den Klartext, den sonst die JVM ausgegeben hätte.
  • Faustregel: Eigene Fehler reparierst du. Fehler von draußen (Tastatur, File, Netzwerk) fängst du.

Das Alles-Quiz: 11 Fragen, 11 Kapitel

Eine Frage pro Kapitel, bunt gemischt. Am besten ein paar Tage nach dem Durcharbeiten: Dein Gehirn liebt verspätete Wiederholung.

1. (Kap. 1) Java-Code wird ausgeführt, indem …

Wie in Kapitel 1: Java wird erst kompiliert, dann interpretiert.

2. (Kap. 2) Welche File gehört zur Klasse public class TrafficLight?

Klassenname = Dateiname. Eine der ersten Fehlermeldungen, die alle mal sehen.

3. (Kap. 3) int x = 7; x = x + 3;: was ist x?

Alten Wert von x lesen, 3 addieren, das Ergebnis wieder in x speichern.

4. (Kap. 4) static double calculatePrice(int quantity): was stimmt?

Signatur lesen: Rückgabetyp vorne, Parameter in den Klammern.

5. (Kap. 5) String s = " Mia "; s.trim(); System.out.println(s.length());: was steht auf der Konsole?

Ein String ändert sich nie. Wer den Rückgabewert will, schreibt s = s.trim();

6. (Kap. 6) In answer steht, was getippt wurde. Wie prüfst du, ob es „yes“ war?

Die eiserne Regel: Zahlen mit ==, Texte mit equals().

7. (Kap. 7) Eine Schleife soll SO LANGE nach einem Passwort fragen, bis es stimmt, mindestens einmal. Welche passt perfekt?

„Erst ausführen, dann prüfen“: Der Schleifenrumpf läuft mindestens einmal. Genau dafür gibt es do-while.

8. (Kap. 8) for (int i = 0; i <= arr.length; i++): wo ist der Fehler?

Gültige Indizes: 0 bis length − 1. Die Bedingung muss i < length heißen.

9. (Kap. 9) Zombie a = new Zombie("Mo", …); Zombie b = a;: wie viele Zombie-Objekte existieren?

Das Zwillings-Experiment: Objekte entstehen nur durch new.

10. (Kap. 10) Neue Zombie-Art „Beisser“ einbauen, without die Fütterungs-Schleife anzufassen: welches Konzept macht's möglich?

Beisser extends Zombie, eigene groan(), die Schleife ruft polymorph auf und muss nichts davon wissen.

11. (Kap. 11) Getippt wird „twelve“ statt einer Zahl, Integer.parseInt wirft eine NumberFormatException. Was ist richtig?

Fehler von draußen (Tastatur, File, Netzwerk) fängt man auf. Den eigenen Fehler repariert man.
