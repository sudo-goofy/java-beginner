11.1 Exceptions and stack trace

Before you catch a crash, you have to be able to read it. The message tells you what happened, where, and how far the program got.

STRUCTURE · CLICK A PART

Exception in thread "main" package.exception type: reason in plain text
   at Class.method(file:line)

Above it, the console shows what the program still printed before the crash.

Exception in thread "main" opens the message: An exception was thrown in the program's main thread and not caught by any catch. That's why the JVM ended the program.
Package: where the exception's class lives, such as java.lang or java.util. For java.lang you don't need an import for a catch, for java.util you do.
Exception type: the name of its class, such as ArrayIndexOutOfBoundsException. The name describes the problem: an index outside the bounds of the array. You will write exactly this name later in the parentheses after catch.
Reason in plain text: the exception's message, such as Index 5 out of bounds for length 3. It often names the values that didn't fit. In the program, e.getMessage() returns it.
Class and method: where the exception was thrown, such as at Crash.main: in the method main of the class Crash. If several at lines are stacked, look for the topmost one that names one of your own classes.
File and line: the source file and the line number in it, such as Crash.java:7. That's where the statement that triggered the exception is, here temperatures[5].

Three elements in the array, one access to index 5. Run it and watch what ends up on the console, and above all, what doesn't.

Crash.java

public class Crash {

    public static void main(String[] args) {
        int[] temperatures = {18, 23, 19};

        System.out.println("All good so far.");
        System.out.println(temperatures[5]);
        System.out.println("This line is never reached.");
    }

}
CONSOLE

LINE BY LINE

ArrayIndexOutOfBoundsExceptionWhat: the exception type. Its package java.lang comes before it.
Index 5 out of bounds for length 3the reason in plain text: with three elements, there is no index 5.
at Crash.main(Crash.java:7)Where: in the method main of the class Crash, file Crash.java, line 7. That's where temperatures[5] is.
All good so far.How far (easy to overlook): This line is still there. Everything before the line with the exception ran, everything after it didn't.

Remember this

An exception is not a syntax error. The program runs, and in the middle of the run a line can't be executed. Java throws an exception and ends the program. That's only the default behavior, and you can change it.

The Panic glossary shows how to get rid of the ten most common errors. Here we deal with the ones you can't get rid of: the fault isn't in your code but in the input.

11.2 Exception handling with try and catch

try means “give it a try,” catch means “catch it.” Together they work like a safety net: The code that can throw an exception goes into the try block. If an exception is thrown there, it lands in the catch block.

STRUCTURE · CLICK A PART

try {
    code that can go wrong
} catch (exception type e) {
    what should happen then
}

After the catch, the program continues normally, with the first line after its closing brace.

try starts the try block. If an exception is thrown inside it, Java aborts the block at that point and looks for a matching catch block. The remaining lines in the try block are skipped, not run later.
Code that can go wrong: the statement that can throw an exception, such as System.out.println(temperatures[5]);, and whatever depends directly on it. Nothing more belongs in here, because when an exception is thrown, everything after it is skipped.
catch comes right after the closing brace of the try block. Its block runs only if an exception of the named type was thrown in the try block. If everything goes smoothly, it is skipped.
Exception type: the class name of the exception, such as ArrayIndexOutOfBoundsException. The catch block catches only this type: If a different one is thrown, the program still aborts.
e is a variable that holds the exception object. You can choose its name freely, e is customary. Section 11.3 shows what you can do with it.
What should happen then: the statements in the catch block, such as System.out.println("That slot does not exist.");. Don't leave the block empty: Otherwise the program keeps running and nobody finds out about the exception.

SafetyNet.java

public class SafetyNet {

    public static void main(String[] args) {
        int[] temperatures = {18, 23, 19};

        try {
            System.out.println("All good so far.");
            System.out.println(temperatures[5]);
            System.out.println("This line is never reached.");
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("That slot does not exist.");
        }

        System.out.println("And on we go.");
    }

}
CONSOLE

LINE BY LINE

try {starts the try block. Everything up to the closing brace is protected.
temperatures[5]throws the exception. Java aborts the try block at this point and looks for a matching catch.
catch (ArrayIndexOutOfBoundsException e)The type matches, so this block runs: “That slot does not exist.”
System.out.println("And on we go.");comes after the catch block. The exception is caught, the program continues normally.

The same program as Crash, just with try and catch around it. That's what the whole chapter is about:

without try/catchwith try/catch
Java ends the program.Java jumps into the catch.
The message goes to the console.You decide what it says.
Everything after it is skipped.After the catch, it keeps going.

And This line is never reached. is missing: The try block runs up to the exception, the rest is skipped, not run afterward. That's why as little as possible belongs in a try block: The more it contains, the more gets skipped.

Remember this

catch catches only the type in its parentheses. catch (ArithmeticException e) doesn't catch an index error: The program then crashes despite the try.

11.3 The exception object

The e in catch (… e) is an ordinary variable holding the exception object. Objects have methods (Chapter 9), and the most important one here is getMessage().

STRUCTURE · CLICK A PART

catch (exception type e) {
    System.out.println(Text + e.getMessage());
}

e has the exception type from the parentheses as its type. getMessage() returns the reason as a String.

Exception type: such as ArithmeticException. It comes before e like the type before a parameter: first the type, then the name.
e holds the reference to the exception object and is only valid inside the catch block. With the dot you call methods of this object, as with any other object.
Text: your own hint before the message, such as "Message: ". Remember the space before the closing quotation mark, otherwise the message sits right against the colon.
The + concatenates the two Strings: "Message: " and "/ by zero" become Message: / by zero.
getMessage() is a method of the exception object. It returns the same message that, without a catch, would appear after the colon in the crash message, such as / by zero. The empty parentheses are part of it.

Excerpt

try {
    int result = 10 / 0;
    System.out.println(result);
} catch (ArithmeticException e) {
    System.out.println("Message: " + e.getMessage());
}
CONSOLE

LINE BY LINE

int result = 10 / 0;divides an integer by 0. Java throws an ArithmeticException, the println below it is skipped.
catch (ArithmeticException e)catches it and puts the exception object into the variable e.
e.getMessage()calls a method of this object. It returns the reason as text: “/ by zero.”

Remember this

e.getMessage() returns the reason the JVM would otherwise have written after the colon, only now exactly where you want it.

11.4 Multiple catch blocks

A try may have several catch blocks. Java goes from top to bottom and takes the first one whose type matches: like an else if for exceptions.

STRUCTURE · CLICK A PART

try {
    code that can go wrong
} catch (first type e) {
    response to the first type
} catch (second type e) {
    response to the second type
}

Order matters: Java checks the catch blocks from top to bottom.

try: a single try block, followed by any number of catch blocks. If an exception is thrown in it, the block aborts at that point, just as with only one catch.
Code that can go wrong: It can throw different types of exceptions. names[2].toUpperCase(), for example, throws an ArrayIndexOutOfBoundsException for an index outside the array and, if the element is null, a NullPointerException. At most one is thrown, though, because the block aborts at the first.
catch: Each block names its own type and has its own response. Once one has matched, all the others are skipped, even if their type would match too.
First type: is checked first, such as ArrayIndexOutOfBoundsException. If Exception stands here, this block catches every exception, and the blocks below would never get their turn. Then the compiler reports an error.
Second type: is checked only if the first one didn't match, such as NullPointerException. If none of the types matches, the program aborts as if there were no try at all.
Response: Each type gets its own reaction, such as “Index is off.” for the index error and “There was nothing.” for null. That's exactly what multiple catch blocks are worth it for.

Excerpt

String[] names = {"Mia", "Paul"};

try {
    System.out.println(names[2].toUpperCase());
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Index is off.");
} catch (NullPointerException e) {
    System.out.println("There was nothing.");
}
CONSOLE

LINE BY LINE

names[2].toUpperCase()names has only the indexes 0 and 1. Even the access to index 2 throws the exception, toUpperCase() is never called.
catch (ArrayIndexOutOfBoundsException e)the first catch. The type matches, so “Index is off.” appears.
catch (NullPointerException e)is skipped: Only the first catch that matches runs.

Remember this

Of several catch blocks, at most one runs: the first one from the top whose type matches.

catch (Exception e) catches everything. Convenient, but rarely right: If you treat everything the same, you can't react differently. You repeat a wrong input, you fix an index error.

11.5 The finally block

After the catch blocks, you may add a finally. It always runs: after a smooth run just as after a caught exception.

STRUCTURE · CLICK A PART

try {
    code that can go wrong
} catch (exception type e) {
    response to the exception
} finally {
    cleanup
}

What for? For cleaning up: closing a file, disconnecting, closing the Scanner. That has to happen even when something went wrong, especially then.

try: runs up to the statement that throws an exception. After that, it continues in the matching catch block and then in the finally block.
Code that can go wrong: such as System.out.println("Per person: " + sum / people);, which, when people equals 0, throws an ArithmeticException. Lines after it in the try block are skipped.
catch with type: The block runs only if an exception of this type was thrown in the try block. If everything goes smoothly, it is skipped, but the finally block is not.
Response to the exception: the reaction to it, such as System.out.println("Cannot divide by 0 people.");. Only after that does the finally block run.
finally comes after the last catch block. Its block runs in every case: after a smooth run, after a caught exception, and even when no type matches and the program aborts afterward.
Cleanup: statements that are always needed, such as keyboard.close(); for the Scanner. What should run only on success doesn't belong here, but in the try block.

LINE BY LINE

try { … }runs up to the line with the exception, the rest is skipped.
catch (…) { … }runs only if a matching exception was thrown.
finally { … }runs either way.

Remember this

finally runs in every case. That's where you clean up.

Exercise 11.5.1: Desk check with finally

Read instead of typing~10 min

Predict the exact output before you run it. Careful with Done.: Look at where the exception is thrown. Afterward: Would Register closing. have appeared even without finally?

Receipt.java

public class Receipt {

    public static void main(String[] args) {
        int sum = 12;
        int people = 0;

        try {
            System.out.println("The bill is being split.");
            System.out.println("Per person: " + sum / people);
            System.out.println("Done.");
        } catch (ArithmeticException e) {
            System.out.println("Cannot divide by 0 people.");

            System.out.println("Register closing.");
        }

        System.out.println("Goodbye.");
    }

}
CONSOLE
Why it works that way
  • Done. is missing, and that's the point: The exception is thrown one line above, the rest of the try block is skipped.
  • Register closing. comes anyway, that's what finally is for.
  • Goodbye. comes after the finally block: The program runs to its normal end.

And without finally? Here Register closing. would also have appeared as a line after the catch, because the exception is caught. finally makes a difference when the catch does not match: Then the program aborts, everything after the finally block is skipped, but the finally block still runs. That's why cleanup belongs there.

11.6 Catching incorrect user input

An index error is your mistake: You fix it. A wrong keyboard input is nobody's mistake: People make typos. If a program crashes because of that, it's badly built, and this is exactly where try/catch pays off.

STRUCTURE · CLICK A PART

try {
    read a number and keep working with it
} catch (InputMismatchException or NumberFormatException e) {
    ask for a new input in a friendly way
}

Which type is thrown depends on how you read. The two approaches below clear that up.

try: If reading throws an exception, the rest of the block is skipped. That way the program never keeps calculating with a number that was never read.
Read a number and keep working with it: such as int age = Integer.parseInt(raw); and then the output with age + 1. Both belong in the try block, because a variable declared there, like age, doesn't exist outside of it.
catch catches only exceptions from its own try block. If the reading happens outside, for example before it, it doesn't protect it.
Type: nextInt() throws an InputMismatchException (import from java.util required), Integer.parseInt throws a NumberFormatException (no import required). With the wrong type in the catch, the program aborts anyway.
Ask for a new input in a friendly way: a message that says what is expected, such as System.out.println("That was not a whole number.");. After that, the program continues normally after the catch block.

If nextInt() doesn't get an integer, the Scanner throws an InputMismatchException. It is in the same package but needs its own line, because an import brings in exactly one class (import java.util.*; brings in the whole package but doesn't reveal what you actually need):

at the very top of the file

import java.util.InputMismatchException;
import java.util.Scanner;

If you read with nextLine() as in Chapter 5 and parse it yourself, Integer.parseInt fails on twelve with a NumberFormatException. It is in java.lang like String, so it needs no import:

Input.java

import java.util.Scanner;

public class Input {

    public static void main(String[] args) {
        Scanner keyboard = new Scanner(System.in);

        System.out.println("How old are you?");
        String raw = keyboard.nextLine().trim();

        try {
            int age = Integer.parseInt(raw);
            System.out.println("Next year: " + (age + 1));
        } catch (NumberFormatException e) {
            System.out.println("That was not a whole number.");
        }
    }

}
CONSOLE

LINE BY LINE

keyboard.nextLine().trim()reads the input as text and removes spaces at the beginning and end, as in Chapter 5.
Integer.parseInt(raw)turns the text into an integer. That doesn't work for “twelve”: Java throws a NumberFormatException, the line below it is skipped.
catch (NumberFormatException e)catches exactly this type and prints a hint instead of letting the program crash.

Remember this

The catch has to match the type, and that depends on how you read:

  • nextInt() throws an InputMismatchException.
  • Integer.parseInt throws a NumberFormatException.

Exercise 11.6.1

Exercise 11.6.1: The calculator that no longer crashes

Basics~15 minIDE

Write a program that reads two integers from the keyboard and divides them. Two things can go wrong: The second number is a 0, or letters come in instead of a number. In both cases the program should not crash, but print a message itself: Nobody divides by zero. or Please enter whole numbers.

The two cases need different tools. Think first: Which one belongs in a catch, which one doesn't?

To try it out, enter: 12, then 0. Then once more with twelve.

Expected output:

Console

Numerator?
Denominator?
Nobody divides by zero.
Solution (try it yourself first)

Calculator.java

import java.util.InputMismatchException;
import java.util.Scanner;

public class Calculator {

    public static void main(String[] args) {
        Scanner keyboard = new Scanner(System.in);

        try {
            System.out.println("Numerator?");
            int numerator = keyboard.nextInt();
            System.out.println("Denominator?");
            int denominator = keyboard.nextInt();

            if (denominator == 0) {
                System.out.println("Nobody divides by zero.");
            } else {
                System.out.println("Result: " + numerator / denominator);
            }
        } catch (InputMismatchException e) {
            System.out.println("Please enter whole numbers.");
        }
    }

}
CONSOLE

Two problems, two tools:

  • You see the 0 coming: An if checks for it before dividing. What you can prevent yourself, you don't catch, you prevent.
  • Letters instead of a number are only noticed by nextInt() while reading: That's what try and catch are for.

The if is inside the try too, because numerator and denominator are only valid there (Chapter 4).

Legendary 11.6.2: The exception you throw yourselfoptional

New~20 minIDE

So far you have caught what Java threw. You can throw yourself too, with throw:

Excerpt

throw new IllegalArgumentException("negative quantity: " + quantity);

The line ends the method immediately like a return, but it doesn't return a value, it passes the exception on to the caller. The caller catches it with catch, otherwise the program crashes. This is how a method rejects an invalid value without inventing a substitute value that nobody can tell apart from an error.

Build a method validate(int quantity) that returns the quantity, but for a negative number throws instead of returning. main calls it for 5 and -3; the second call lands in the catch, which prints e.getMessage().

Expected output:

Console

Ammo: 5
Rejected: negative quantity: -3
Solution (try it yourself first)

Guard.java

public class Guard {

    public static void main(String[] args) {
        int[] attempts = {5, -3};

        for (int v : attempts) {
            try {
                System.out.println("Ammo: " + validate(v));
            } catch (IllegalArgumentException e) {
                System.out.println("Rejected: " + e.getMessage());
            }
        }
    }

    static int validate(int quantity) {
        if (quantity < 0) {
            throw new IllegalArgumentException(
                    "negative quantity: " + quantity);
        }
        return quantity;
    }

}
CONSOLE

Two things are new:

  • After throw, there is no return: The method is over after that, and the compiler knows it.
  • The try is inside the loop, not around it. If it were outside, it would be over after the first rejected attempt.

The text in the parentheses is exactly what getMessage() returns later. So what belongs there is what the caller needs to know, not “Error!”.

Situation: A warehouse program reads the quantity from the keyboard and calculates the total price (€2.50 per item). At the acceptance test, the customer types twelve instead of 12, and the program aborts.

Solution (try it yourself first)

a) An InputMismatchException, thrown by keyboard.nextInt() in line 2. nextInt() expects an integer and gets letters.

b)

CampOk.java

import java.util.InputMismatchException;
import java.util.Scanner;

public class CampOk {

    public static void main(String[] args) {
        Scanner keyboard = new Scanner(System.in);

        System.out.println("Quantity?");

        try {
            int quantity = keyboard.nextInt();
            System.out.println("Total price: " + quantity * 2.5 + " euros");
        } catch (InputMismatchException e) {
            System.out.println("Please enter a whole number.");
        }

        System.out.println("Next item.");
    }

}
CONSOLE

The output line has to go in the try block too: quantity is declared in the try and is only valid there (Chapter 4). At the top you also need import java.util.InputMismatchException;.

c) Two possible disadvantages of catch (Exception e):

  • It also catches what wasn't meant: index errors, NullPointerException, every programming error. The program seems to keep running, and the error only shows up much later.
  • If you treat everything the same, you can no longer react differently.

Checkpoint

The try block contains three println statements. The second one throws an exception. How many lines from the try block appear?

That's why as little as possible belongs in a try block.

When does a finally block run?

That's why you clean up there: closing a file, closing the Scanner.

catch (ArithmeticException e) is placed around an array access. What happens on the index error?

The program crashes despite the try. The type has to match.

Which error do you catch with catch, and which one do you fix?

What comes from outside (keyboard, file, network) you catch. Your own mistake you fix.

The key points

  • An exception is not a syntax error, but an event at runtime.
  • try wraps the risky code, catch (Type e) catches exactly this type.
  • In a try, everything after the line with the exception is skipped: put in as little as possible.
  • finally runs in every case. That's where you clean up.
  • e.getMessage() returns the plain text the JVM would otherwise have printed.
  • Rule of thumb: You fix your own errors. Errors from outside (keyboard, file, network) you catch.
